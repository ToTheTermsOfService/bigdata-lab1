# ЛР1. Побудова регресійних моделей — Варіант 6: рейтинг фільму та прогноз доходу

.NET 10 + ML.NET 5.0, датасет [TMDB 5000 Movie Metadata](https://www.kaggle.com/datasets/tmdb/tmdb-movie-metadata) (`data/tmdb_5000_movies.csv`).

## Завдання: Варіант 6 «Рейтинг фільму та прогноз доходу»

Витрати на виробництво іноді перевищують 100 мільйонів доларів, тож фільми є значними інвестиціями. Проте успіх фільму залежить не лише від витрачених грошей. Моделі прогнозування касових зборів дають інвесторам логічний спосіб вибирати фільми для інвестування і збільшувати шанси на успіх. Для реалізації варіанта використана багатофакторна регресійна модель; методичка також дозволяє інші регресійні моделі, тому в роботі порівняні всі доступні в ML.NET тренери регресії. Набір даних — запропонований у варіанті TMDB Movie Metadata.

Відповідно до завдання побудовано **дві моделі**: прогноз **доходу** (касових зборів) і прогноз **рейтингу** фільму.

## Структура

Дві незалежні частини, як вимагає методичка:

| Частина | Проєкт | Що робить |
|---|---|---|
| 1. Тренування, оцінювання, серіалізація | `src/MovieRevenue.Trainer` (консоль) | читає CSV, чистить дані, тренує 9 регресійних тренерів, порівнює їх, зберігає найкращу модель у `models/*.zip` |
| 2. Завантаження/десеріалізація, використання | `src/MovieRevenue.Api` (Web API + Swagger) | завантажує `.zip` моделі та віддає прогнози через HTTP |
| спільне | `src/MovieRevenue.Core` | схема даних (`ModelInput`), читання CSV, побудова ознак — однакова в обох частинах |

## Дві моделі

1. **Дохід** (`revenue-model.zip`): прогноз `revenue`. Ознаки: бюджет, популярність, тривалість, середня оцінка, кількість голосів, рік і місяць релізу, жанри, мова.
2. **Рейтинг** (`rating-model.zip`): прогноз `vote_average` (0–10) без голосів: бюджет, тривалість, дата, жанри, мова та популярність. Голоси й рейтинг не використовуються як ознаки, бо це була б «підказка відповіді». В API, якщо не передати `voteAverage`, модель доходу бере прогноз моделі рейтингу. Так дві моделі працюють ланцюжком.

## Процес навчання (що розповідати на захисті)

1. **Читання даних.** Колонка `genres` зберігає JSON (`[{"id":28,"name":"Action"}]`), а в описах трапляються коми та переноси рядків. Тому замість `TextLoader` використано `TextFieldParser` з ручним розбором JSON.
2. **Очищення.** 4802 фільми з датою релізу. Для доходу залишено фільми з `budget ≥ $10 000` і `revenue ≥ $10 000`, бо нулі означають «невідомо», а значення на кшталт «1» чи «12» записані в мільйонах. Лишилося **3205** фільмів. Для рейтингу беремо фільми з `vote_count ≥ 20`, бо при меншій кількості голосів оцінка випадкова. Лишилося **4137** фільмів.
3. **Ознаки (feature engineering):**
   - `log(1 + x)` для бюджету, доходу, популярності та голосів. Ці величини сильно скошені (кілька блокбастерів на мільярди), а логарифм робить розподіл майже нормальним. Тому модель доходу вчиться на `log(1 + revenue)`, а API повертає `exp(score) − 1`.
   - Дата релізу розкладається на рік і місяць.
   - Жанри кодуються multi-hot вектором довжини 20.
   - Мова кодується one-hot у пайплайні ML.NET (`OneHotEncoding`).
4. **Пайплайн ML.NET:** `OneHotEncoding(мова) → Concatenate(Features) → NormalizeMinMax → тренер`.
   - MinMax, а не MeanVariance: після MeanVariance рідкісні one-hot колонки отримували величезні значення, і OnlineGradientDescent розходився (R² ≈ −70 000).
   - Для `Ols` задано L2-регуляризацію, бо без неї матриця XᵀX вироджена.
5. **Оцінювання.** Дані діляться на train і test у пропорції 80/20 з фіксованим seed. Для кожного тренера рахується **5-fold крос-валідація** на train, а потім оцінка на відкладеному test. Найкращого тренера обираємо за **середнім CV R²**, а не за test, щоб test залишався чесною перевіркою.
6. **Серіалізація.** Команда `mlContext.Model.Save(model, schema, "*.zip")` зберігає весь пайплайн разом із кодуванням мови й нормалізацією, а не лише ваги. Поруч записується `*.json` з метриками всіх тренерів і важливістю ознак, його показує `GET /api/model/info`.
7. **Використання.** API завантажує моделі через `PredictionEnginePool` з пакета Microsoft.Extensions.ML. Це потокобезпечна обгортка над `mlContext.Model.Load` + `PredictionEngine`, бо звичайний `PredictionEngine` не можна ділити між потоками.

## Результати

### Модель доходу (мітка `log(1 + revenue)`, train 2564 / test 641)

| Тренер | CV R² | Test R² | Test MAE (log) | MAE, $M | Медіанна похибка |
|---|---|---|---|---|---|
| **LightGbm** ✅ | **0.658 ± 0.022** | 0.675 | 0.663 | **48.3** | **42%** |
| Gam | 0.654 ± 0.021 | 0.689 | 0.680 | 54.8 | 47% |
| FastTreeTweedie | 0.650 ± 0.026 | 0.668 | 0.664 | 48.9 | 44% |
| FastTree | 0.649 ± 0.027 | 0.678 | 0.659 | 49.5 | 43% |
| FastForest | 0.625 ± 0.009 | 0.652 | 0.725 | 60.1 | 48% |
| Sdca | 0.624 ± 0.018 | 0.672 | 0.682 | 52.8 | 45% |
| LbfgsPoisson | 0.624 ± 0.022 | 0.650 | 0.719 | 61.5 | 49% |
| Ols | 0.562 ± 0.011 | 0.609 | 0.775 | 64.9 | 51% |
| OnlineGradientDescent | 0.412 ± 0.024 | 0.444 | 0.957 | 86.5 | 63% |

Важливість ознак для LightGbm (на скільки падає R², якщо перемішати ознаку): кількість голосів **0.77**, бюджет **0.24**, рік **0.14**, жанри 0.08, оцінка 0.04. Решта ознак дає менше 0.02.

### Модель рейтингу (мітка `vote_average`, train 3310 / test 827)

| Тренер | CV R² | Test R² | Test MAE |
|---|---|---|---|
| **Gam** ✅ | **0.514 ± 0.034** | 0.502 | 0.473 |
| LightGbm | 0.505 ± 0.015 | 0.528 | 0.461 |
| FastTree | 0.502 ± 0.017 | 0.518 | 0.466 |
| FastTreeTweedie | 0.499 ± 0.021 | 0.531 | 0.465 |
| FastForest | 0.415 ± 0.023 | 0.415 | 0.526 |
| LbfgsPoisson | 0.413 ± 0.040 | 0.399 | 0.531 |
| Sdca | 0.396 ± 0.046 | 0.378 | 0.540 |
| Ols | 0.350 ± 0.034 | 0.318 | 0.565 |
| OnlineGradientDescent | 0.091 ± 0.061 | 0.068 | 0.659 |

Важливість ознак: популярність **0.60**, жанри **0.25**, бюджет 0.18, тривалість 0.11, рік 0.10.

### Висновки

- **Нелінійні моделі** (бустинг дерев і GAM) стабільно кращі за лінійні: +0.03…0.25 R². Методичка каже про це прямо: лінійна регресія не враховує взаємодій між ознаками. Наприклад, ефект бюджету залежить від жанру і року.
- **Gam** майже не поступається бустингу і при цьому інтерпретований: кожна ознака дає окрему функцію-внесок. Однак експорт в ONNX для нього не підтримується.
- **OnlineGradientDescent** найгірший: це один прохід SGD без підбору кроку навчання, і він чутливий до масштабу ознак.
- Похибка в доларах велика (медіана близько 42%): касові збори залежать від маркетингу, акторів, конкурентів у прокаті, франшиз тощо, а цих даних у датасеті немає.
- **Обмеження:** найсильніша ознака моделі доходу, `vote_count`, з'являється вже **після** релізу. Тож модель доходу найкраще описує сценарій «прогноз після перших тижнів прокату». Для прогнозу до релізу в API можна не передавати `voteAverage`, тоді його дасть модель рейтингу. Але `voteCount` все одно потрібно оцінити самостійно.
- **Обмеження моделі рейтингу:** найсильніша її ознака, популярність TMDB (падіння R² 0.60), теж накопичується **після** релізу. Тож і ця модель не є «чисто дорелізною»: для ще не випущеного фільму популярність доводиться оцінювати вручну, наприклад за аналогічними фільмами. Якщо прибрати популярність, модель спиратиметься лише на справжні дорелізні ознаки, але R² помітно впаде.

## API

| Метод | Шлях | Опис |
|---|---|---|
| POST | `/api/predict/revenue` | прогноз доходу, прибутку та ROI |
| POST | `/api/predict/rating` | прогноз середньої оцінки |
| GET | `/api/model/info` | обраний тренер, таблиця всіх тренерів, важливість ознак |
| GET | `/api/genres` | допустимі жанри |

Приклад запиту (він же підставлений у Swagger):

```json
{
  "title": "Dune: Part Three",
  "budget": 190000000,
  "runtime": 155,
  "releaseDate": "2026-12-18",
  "genres": ["Science Fiction", "Adventure"],
  "originalLanguage": "en",
  "popularity": 80,
  "voteAverage": null,
  "voteCount": 4000
}
```

Відповідь: `predictedRevenueUsd ≈ 615 000 000`, `returnOnInvestment ≈ 3.24`, `voteAverageUsed = 6.65` (`voteAverageSource: "rating-model"`).
